# HBX 05-06 atualizacao

Documento de preparo para uma aplicacao grande e controlada em branch, baseada no material colado em 05/06/2026.

Branch operacional criada para este plano:

```txt
05-06-atualizacao
```

Observacao: o nome pedido, `05-06 atualização`, foi recusado pelo Git como nome de branch invalido. A branch criada usa a forma segura `05-06-atualizacao`.

## Intencao

Este arquivo nao e uma ordem para aplicar tudo de uma vez.

O objetivo e separar a atualizacao em passos grandes o bastante para resolver o problema real, mas pequenos o bastante para:

- revisar diff por diff;
- testar cada bloco antes de puxar o proximo;
- evitar refactor amplo;
- preservar auth, billing, planos, pagamentos, secrets, migrations e producao sob controle manual;
- manter o fluxo principal do HBX: Radar -> Vendas -> WhatsApp -> Retorno.

## Estado alvo

Ao final da fila, o HBX deve ter:

- vendedor de empresa cliente governado pelo Admin da propria empresa;
- vendedor da operacao HBX governado pelo Master HBX;
- desktop e mobile usando a mesma regra de capacidade;
- Radar bloqueado por quota ativa antes de fazer busca cara;
- dedupe por contato comercial dentro da mesma carteira/companyId;
- negativos e historico comercial preservados;
- testes cobrindo acesso, quota, dedupe e fluxos principais;
- PR revisavel, com commits pequenos por tema.

## Travas de seguranca

Durante a execucao dos passos:

- nao alterar pricing, planos, paywall, quotas comerciais de cobranca, billing, checkout, webhooks, refunds ou assinaturas;
- nao expor secrets, tokens, `.env`, dados sensiveis ou PII em logs;
- nao fazer deploy, publish, restart de producao, merge automatico ou migration automatica;
- nao apagar historico negativo, status final, owner, follow-up ou dados comerciais para "resolver rapido";
- nao liberar modulo pago ou administrativo por fallback frontend;
- qualquer mudanca de schema Prisma que exija migration deve virar HOLD explicito para revisao do dono antes de executar migration.

## PASSO 06 - Radar para antes da busca cara quando quota estiver cheia

Objetivo:

- impedir custo desperdicado;
- parar antes de Google/premium/webscraping quando nao ha slot disponivel.

API alvo:

```ts
export function resolveRadarSearchAllowance(input: RadarQuotaCheckInput): {
  ok: boolean;
  code: 'OK' | 'SELLER_CARD_QUOTA_REACHED';
  activeCount: number;
  effectiveLimit: number;
  availableSlots: number;
  allowedLimit: number;
};
```

Regras:

- contar cards ativos do vendedor;
- calcular `availableSlots = effectiveLimit - activeCount`;
- se `availableSlots <= 0`, nao chamar busca cara;
- se `availableSlots > 0`, limitar `requestedLimit` ao menor valor entre slots, plano e limite diario;
- retornar `SELLER_CARD_QUOTA_REACHED` com mensagem em PT-BR.

Acoes:

1. Localizar ponto exato antes da chamada cara do Radar.
2. Inserir check de quota antes da chamada.
3. Limitar o tamanho da busca quando houver poucos slots.
4. Preservar negativos e historico.
5. Criar testes garantindo que a funcao cara nao e chamada com quota cheia.

Testes minimos:

- quota cheia retorna `SELLER_CARD_QUOTA_REACHED`;
- quota cheia nao chama provider caro;
- quota parcial reduz requestedLimit;
- quota disponivel cria no maximo o permitido.

Validacao:

```powershell
npm --prefix backend run build
```

Criterio de aceite:

- Radar para antes da busca cara;
- nenhum fallback cria card fora da quota;
- logs nao exponhem dados sensiveis.

Regras:

- quando permitido, retornar status e responsavel existente;
- nao fazer primeiro contato automatico em duplicidade.

Acoes:

4. Aplicar dedupe antes de criar card/contato ativo.

Criterio de aceite:
