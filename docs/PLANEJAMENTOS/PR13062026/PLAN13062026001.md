## E1 — Exclusão de empresa órfã CORRIGIDA (13/06/2026) — ⏳ aguarda restart prod

**Problema (relatado pelo dono):** ao excluir uma empresa, a conta admin continuava
logando e caía em 503 no Dashboard/Atendimento; tudo zerado. Empresa/usuário órfãos.

**Causa raiz:** havia DOIS caminhos de exclusão divergentes:
- `@Delete('master/:id')` → `removeByMaster` → `permanentlyDeleteCompanyInternal` —
  COMPLETO (apaga dados + sessões WhatsApp + **usuários** na linha ~1189, protege master).
- `@Delete(':id')` (Admin) → `removeForCompany` — **INCOMPLETO**: fazia `tx.company.delete()`
  direto. Como a relação `User.company` no schema é `Company?` **sem `onDelete`** (default
  Prisma = **SetNull**), os usuários sobreviviam com `companyId` nulo (e o JWT antigo ainda
  apontava pra empresa inexistente) → órfãos presos em 503 (`inbox.service.ts:599`).

**Correção aplicada (build verde back+front):**
- `backend/src/companies/companies.service.ts`: `removeForCompany` agora **delega para
  `permanentlyDeleteCompanyInternal`** (mesma cascata completa do master, apaga usuários).
  Novo `mode: 'admin_self_delete'` + `ADMIN_COMPANY_DELETE_MODULE_KEY` (auditoria).
- `backend/src/companies/companies.controller.ts`: `remove()` passa `req.user?.id`
  (registro de quem excluiu).
- Garantia "não volta a acontecer": agora **só existe 1** `tx.company.delete` no código
  (dentro da cascata completa). Nenhum caminho de app orfana usuário.

**Mudança de comportamento (avisar o dono):** o `DELETE /companies/:id` do admin agora faz
exclusão TOTAL e irreversível (empresa + TODOS os usuários, inclusive o próprio admin). Não
há UI chamando essa rota (o /master usa o caminho `master/:id`), então sem impacto de tela.

**Pendências / decisões do dono:**
1. **Estado órfão ATUAL** (a conta `jhonatan@` que já ficou órfã) NÃO é limpo por código —
   é dado em produção. Opções: recriar a empresa + reconectar WhatsApp, ou limpar o usuário
   órfão no banco (cirurgia de dado = o dono faz).
2. **Hardening opcional (NÃO aplicado — aguarda ordem):** mudar `User.company` para
   `onDelete: Restrict` no schema (migration) faria o BANCO recusar apagar empresa com
   usuários — proteção mesmo contra DELETE direto no banco. É migration = só com ordem.

**Frontend (JÁ no ar, sem restart):** aviso de "empresa removida". `AuthGate` detecta
usuário não-master sem empresa (`/profile/current-user` → `company:null`) e faz saída limpa
pro `/login` com aviso, em vez de telas em 503. Arquivos: `auth-gate.tsx`, `shell.tsx`
(tipo `CurrentUser.company`), `login/page.client.tsx` (texto do aviso).

## E2 — Inbox sem WhatsApp NÃO grita mais 503 + CTA de conexão (14/06/2026) — ⏳ aguarda restart prod

**Problema (relatado pelo dono):** o `/inbox/conversations` devolvia **503**
"Atendimento indisponível sem WhatsApp/celular vinculado" no load do Dashboard, Topbar e
Atendimento — vermelho gritando no console mesmo em aba anônima. Além disso o dono não
achava o lugar pra **vincular** o WhatsApp.

**Causa:** `inbox.service.ts` lançava 503 em `listConversations` (linha ~3955) e no
`listPersistedConversationSummariesForCompany` (~3351) via `assertInboxWhatsappAccessible`
quando a empresa não tinha nenhum dos 3 trilhos de WhatsApp.

**Correção aplicada (build verde, inbox-smoke 33/33, lint/catraca 576/576):**
- `backend/src/inbox/inbox.service.ts`: nas DUAS rotas de listagem, troquei o
  `assertInboxWhatsappAccessible` por `if (!sessionScope.accessible) return [];` →
  **lista vazia (200)** em vez de 503. As linhas já eram filtradas por `isRowVisible...`,
  então o resultado é o mesmo, só sem o erro. O 503 raro "conectado mas sessão não criada"
  (`webwhats_status_only`) foi mantido de propósito (estado acionável). As rotas de AÇÃO
  (start/send) seguem barrando — não disparam no load.
- `frontend/.../atendimento/page.client.tsx`: empty-state agora mostra texto manso +
  botão **"Conectar WhatsApp"** (abre o `WhatsAppConnectModal`) quando `waStatus !== connected`.
  A pílula "● WhatsApp" do topo já abria o modal; agora há um CTA óbvio também na lista vazia.

**Efeito:** Dashboard "Atendimentos em aberto" mostra **0** (não "—"), sem 503 no console;
Atendimento abre normal e oferece o botão de conectar. O aviso "some" sozinho quando o
WhatsApp é vinculado. Backend espera restart; frontend entra no próximo deploy do front.
