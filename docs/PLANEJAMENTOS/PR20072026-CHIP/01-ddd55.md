# Worker 01 — BLOCO B: bug de normalização DDD 55

## Problema
Número BR de 11 dígitos que começa com "55" (DDD 55 = Rio Grande do Sul: Santa Maria, Uruguaiana,
Bagé) é confundido com "já tem DDI 55" e sai SEM país. Ex.: `55999923190` → `+55999923190` (DDD
comido) → Webwhats recusa (Bad Request). Provado no incidente: lead SMART WORKSHOP, conversa 2501,
3 tentativas FAILED. **Todo lead com DDD 55 quebra** — e a Gabriele prospecta o RS.

A regra errada está **copiada em 3 lugares**, todas com a mesma condição furada
`!digits.startsWith('55') && (length === 10 || 11)`:
1. `backend/src/messaging/whatsapp-channel.ts:60-66` — `normalizeBrPhoneDigits` (FONTE canônica).
2. `backend/src/messaging/messaging.service.ts:2212-2220` — `normalizeSelfAlertPhone`.
3. `backend/src/vendas/vendas-automation.service.ts:451-458` — `normalizePhoneDigits`.

## Causa
Decidir "tem DDI?" pelo **prefixo 55** é ambíguo — DDD 55 colide com DDI 55. A decisão correta é por
**comprimento**: telefone BR sem país tem 10 (fixo) ou 11 (celular) dígitos e **nunca** contém DDI;
com país tem 12 ou 13. Logo: 10 ou 11 dígitos → SEMPRE falta o 55, prefixar. Nunca olhar prefixo.

## Mudança
### 1. `whatsapp-channel.ts#normalizeBrPhoneDigits` (fonte única)
Trocar a condição para depender só do comprimento:
```ts
export function normalizeBrPhoneDigits(valueRaw: string | null | undefined): string {
  const digits = normalizeWhatsAppDigits(valueRaw);
  if (!digits) return '';
  // BR sem país = 10 (fixo DDD+8) ou 11 (celular DDD+9) dígitos; nunca contém DDI.
  // Decidir por COMPRIMENTO, não por prefixo — DDD 55 (RS) colide com DDI 55.
  if (digits.length === 10 || digits.length === 11) return `55${digits}`;
  return digits;
}
```
Conferir `buildWhatsAppPhoneCandidates` no mesmo arquivo (linha ~75): tem o mesmo padrão
`!startsWith('55') && (10|11)` ao ADICIONAR candidatos. Como ele gera um CONJUNTO de tentativas (não
um valor único), o risco é menor, mas **alinhar**: para 10/11 dígitos, sempre incluir a variante
`+55<digits>`/`55<digits>` (tirar o `!startsWith('55')`). Manter as demais variantes que já existem.

### 2. `messaging.service.ts#normalizeSelfAlertPhone` e 3. `vendas-automation.service.ts#normalizePhoneDigits`
Não duplicar de novo: **reusar a fonte única**. Importar de `../messaging/whatsapp-channel`
(`normalizeBrPhoneDigits`) e reescrever cada função como wrapper fino que preserva o
contrato/retorno atual de cada uma:
- `normalizeSelfAlertPhone(value)` → usa `normalizeBrPhoneDigits`, mantém o clamp
  `length < 10 || length > 15 → null` e o retorno `+${digits}`.
- `normalizePhoneDigits(raw)` (vendas-automation) → usa `normalizeBrPhoneDigits`, mantém retorno
  `digits || null`.
Se o import gerar ciclo de dependência, deixar a função local MAS com a condição corrigida por
comprimento (o que importa é a REGRA certa nos 3; a dedup é secundária).
